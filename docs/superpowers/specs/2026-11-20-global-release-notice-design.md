# 全站版本更新公告设计

日期：2026-11-20

状态：已实现并发布

## 目标

- 每次发布新版本时，向所有宿舍成员提示用户可理解的新增内容。
- 公告不依赖房主操作，由版本发布自动触发。
- 同一成员错过多个版本时，把所有错过的更新合并成同一次弹窗。
- 弹窗使用与房型变更通知相同的“知道了”确认形式。

## 发布范围

- 公告是全站公告，覆盖所有宿舍和所有成员账号。
- 房主也会收到版本更新公告。
- 新注册成员也会收到当前版本对应的历史累计公告。
- 公告内容由发布时人工整理成简单易懂的用户摘要，不直接使用 Git 提交信息。

## 内容密度

- 每次发布支持多条用户摘要。
- 同一成员错过多个版本时，将所有错过的摘要平铺在同一个弹窗内。
- 弹窗顶部显示版本范围，例如 `1.0.0 -> 1.3.0`。
- 不按版本分组展示正文，只显示一份平铺摘要。
- 摘要较多时，弹窗正文允许纵向滚动。

## 领取与去重

- 公告不在版本部署瞬间打断正在使用页面的成员。
- 成员下一次打开页面、从后台回到前台、绑定新设备或恢复账号时领取公告。
- 普通 5 秒轮询不会领取版本公告。
- 版本公告按成员账号记录，每个账号对同一版本只提示一次。
- 同一账号多台设备中，只向最先访问的一台设备发送公告。
- 点击“知道了”后，同账号其他设备都不再显示这次公告。
- 如果第一台设备收到公告但未确认，服务器仍视为已经发送。

## 累计计算

- 成员记录已阅读版本。
- 公告摘要从“成员上次已读版本之后”算到当前最新版本。
- 已经看过 `1.2.0` 的成员，在 `1.3.0` 发布后只会看到 `1.3.0` 的摘要。
- 错过多个版本的成员，会看到从上次已读版本到最新版的合并摘要。
- 没有已读版本的新成员，从 `1.0.0` 开始累计。
- 已有账号没有已读版本字段时，也按从 `1.0.0` 开始处理。

## 弹窗优先级

同一成员同时有待看的版本公告和房型变更通知时：

1. 先显示版本更新公告。
2. 成员点击“知道了”后，如果还有未看的房型通知，立即接着显示房型通知。
3. 新成员创建或加入时，先完成必须保存恢复码的弹窗，再显示版本更新公告。

## 自动发布

- 应用版本号和用户摘要清单一起进入代码仓库。
- 部署新版本时，云函数读取当前应用版本对应的发布摘要。
- 相同版本重复部署不会产生新的公告。
- 新版本发布后，新前端初始化时携带领取公告的标记，云端再向该账号投放摘要。
- API 先部署而静态前端尚未更新时，旧前端不会领取或消耗新公告。

## 强制校验

部署前必须检查：

- `package.json` 中的应用版本存在于发布摘要清单。
- 该版本至少包含一条非空用户摘要。
- 版本号必须可比较且严格递增。
- 校验失败时，`npm run deploy` 必须直接终止，不能只打印警告。

## 云端数据

成员新增：

- `lastSeenReleaseVersion`：最近已经领取过的应用版本。
- `releaseNoticeDeliveredAt`：最近领取时间。

独立记录公告领取凭据，确保同账号多设备只能领取一次：

- `memberId`
- `fromVersion`
- `toVersion`
- `claimedAt`

领取凭据必须具有账号级唯一性，并由最先访问的设备获得。

## 首批累计公告

本次公告系统完成后，发布一份覆盖 `1.0.0` 到最新版的累计更新，至少包含：

- 四人寝与六人寝状态共享
- 四种成员状态、留言和自动过期
- 多设备账号、绑定码和账号恢复码
- 设备查看、撤销和单独退出
- 创建与切换四人寝、六人寝
- 房型变更保护和成员通知
- 0 到 6 人休息颜色层级
- 全站版本更新公告

## 验收重点

- 新版本部署后，成员只在下次访问时收到公告。
- 普通轮询和保持页面打开不会提前收到公告。
- 同一账号两个设备只由最先访问的设备收到公告。
- 错过多个版本时只出现一个弹窗，摘要合并且可滚动。
- 新成员先保存恢复码，再看到从 1.0 开始的累计公告。
- 同时存在版本公告和房型通知时，版本公告先显示，确认后房型通知继续。
- 版本号与发布摘要不一致时，部署失败。
- 同一版本重复部署不会重复提示。
