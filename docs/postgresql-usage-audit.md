## 1. 检修结论

按当前证据，PostgreSQL 用量偏高的主要原因排序如下：

1. **用户在线期间的持续 API 活动，尤其是首页 5 秒轮询。**
   - 代码已确认：页面可见时每 5 秒调用一次 `getState`。
   - 云端已确认：当前计费周期 PostgreSQL 使用 `15,350` 核秒，折合约 `102.3` 个 5 分钟活跃时间段，对应约 `1,458.28` 资源点。
   - 判断：活跃时间段是目前共享实例计算用量的直接来源，而不是单纯由查询次数造成。

2. **每次 `getState` 固定产生 3 次写入，设备在线时间被重复写入。**
   - 代码已确认：正常 `getState` 为 5 次读取、3 次写入。
   - 代码已确认：认证阶段先更新一次 `deviceSessions.lastSeenAt`，构建状态时又更新一次同一设备。
   - 云端已确认：数据库累计统计中 `members` 更新 `1,961` 次、`deviceSessions` 更新 `3,239` 次；同期 `statuses` 仅更新 `74` 次。写入高度集中在在线时间字段。

3. **每小时清理任务已真实启用，会在无用户访问时单独制造数据库活跃时间段。**
   - 云端已确认：`dormsyncCleanup` 为 Active，触发器 `hourly-room-cleanup` 已启用，Cron 为 `0 0 * * * * *`。
   - 近 24 小时按小时监控显示，最近 7 个小时各有 1 次调用，说明定时器确实执行。
   - 其单独影响上限为每天 24 个活跃时间段、约 342 资源点；但当前 PostgreSQL 已出现约 102 个活跃时间段，远高于只有清理任务的 24 个，因此它不是本轮用量的主因。

4. **状态变更、Bark 设备更新、冷启动建集合检查属于次要来源。**
   - 状态实际更新少，Bark 当前业务数据也很少。
   - 冷启动会执行 9 次集合创建检查，增加数据库请求，但通常发生在已有用户请求或清理任务的同一活跃时间段内，不是活跃时间段数的主要决定因素。

5. **没有发现慢查询、锁等待或磁盘 I/O 是主要矛盾的证据。**
   - 当前数据库连接均为 idle，未观察到长事务或活跃慢查询。
   - 数据库缓存命中约 `99.97%`，累计临时文件为 0，死锁为 0。
   - 但 `pg_stat_statements` 未启用，CLI 慢查询命令只覆盖 MySQL，日志服务也未启用，因此不能宣称已经完成 SQL 级慢查询审计。

### 3.1 `getState` 的 5 读 3 写

正常热路径：

1. 按 token hash 查询 `deviceSessions`：1 读。
2. 按 `memberId` 读取 `members`：1 读。
3. 认证阶段更新 `deviceSessions.lastSeenAt`：1 写。
4. 读取 `rooms`：1 读。
5. 读取活跃 `members`：1 读。
6. 读取 `statuses`：1 读。
7. 更新当前 `members.lastSeenAt`：1 写。
8. 再次更新当前 `deviceSessions.lastSeenAt`：1 写。

因此同一普通轮询请求中，同一设备的 `lastSeenAt` 确实写入两次。

以下条件会额外增加操作：

- 任一状态过期：每个过期状态 +1 写，且自动过期不会发送通知。
- 旧版“预计时间已结束”留言清理：每个待清理状态 +1 写。
- 存量未验证寝室房主首次进入：+1 次房间写入。
- 领取容量公告：+1 次成员条件更新。
- 领取版本公告：`releaseClaims` 新增 + 成员更新，通常 +2 写。
- 冷实例首次建立集合：额外 9 次 schema 检查。

## 4. 轮询与活跃时间段模型

### 4.1 请求量和数据库操作量

单个页面持续可见时：

- `12` 次 `getState` / 分钟。
- `720` 次 / 小时。
- `5,760` 次 / 8 小时。
- 每次普通 `getState` 为 5 读 3 写，共 8 次 SDK 数据库操作：
  - `96` 次数据库操作 / 分钟；
  - `5,760` 次 / 小时；
  - `46,080` 次 / 8 小时。

| 场景 | API 请求 / 分钟 | 数据库操作 / 分钟 | 8 小时内活跃 5 分钟时间段 |
|---|---:|---:|---:|
| 1 个页面可见 | 12 | 96 | 最多 96 |
| 同一账号 2 个标签页 | 24 | 192 | 最多 96 |
| 2 台设备同时在线 | 24 | 192 | 最多 96 |
| 4 人寝、每人 1 个可见页面 | 48 | 384 | 最多 96 |
| 6 人寝、每人 1 个可见页面 | 72 | 576 | 最多 96 |

同时在线设备的增加会线性放大 API 调用和数据库读写，但只要所有活动落在同样的 5 分钟窗口内，PostgreSQL 活跃时间段不会按设备数线性增加。

### 4.2 5 秒改 30 秒

若页面持续可见：

- API 调用从 720 次 / 小时降至 120 次 / 小时，减少约 83.3%。
- 数据库 SDK 操作从 5,760 次 / 小时降至 960 次 / 小时，减少约 83.3%。
- 如果页面始终每 5 分钟至少访问一次数据库，**活跃时间段仍可能完全相同**。

因此，延长轮询首先降低函数、数据库请求负载和响应压力；是否降低 PostgreSQL 计算资源点，要看它是否真的让部分 5 分钟窗口完全无数据库访问。

## 6. 定时清理核实

- `dormsyncCleanup` 已部署，状态 Active。
- Handler：`index.cleanup`。
- Trigger：`hourly-room-cleanup`，类型 timer。
- Cron：`0 0 * * * * *`。
- 触发器创建时间：2026-11-21 04:50:34。
- 近 24 小时小时监控显示最近 7 个小时各调用 1 次。
- 云函数错误和超时均为 0。

清理任务的数据库路径：

- 热实例、room verification rollout 已缓存：通常只扫描一次 `rooms`。
- 冷实例：额外执行 9 次建集合检查，并读取一次 `systemSettings`。
- 只有未验证且超过截止时间的寝室才进入删除链路；已验证寝室不会逐间读取成员。
- 当前约 36 个房间时，正常热清理为 1 次读取，不产生写入。

无用户访问时，每小时清理最多形成 24 个独立活跃时间段：

- 每天：`24 × 14.25 = 342` 点。
- 30 天：约 `10,260` 点。

但这是上限。若清理恰好与用户请求处于同一 5 分钟窗口，不会额外增加该时间段。当前观测到约 102 个活跃时间段，已经显著高于“只有每小时清理”的 24 个，因此清理不是首日主因。

## 7. 根因排序

### P0-1：可见页面 5 秒轮询造成的数据库活跃时间

- 证据级别：代码已确认 + 云端用量支持。
- 影响：决定数据库是否在大量 5 分钟窗口内保持活跃。
- 当前判断：最可能的主要资源点来源。

### P0-2：重复且高频的在线时间写入

- 证据级别：代码已确认 + 云端累计更新统计支持。
- 影响：每次 `getState` 3 写，其中设备会话在同一请求内写两次。
- 注意：减少写入会降低数据库负载，但只要读轮询仍持续触发，5 分钟计算用量未必同步下降。

### P0-3：每小时清理制造的无用户活跃窗口

- 证据级别：云端已确认。
- 影响：每天最多 342 点；当用户完全离线时，它会成为唯一持续来源。

### P1：冷启动集合检查

- 证据级别：代码已确认。
- 影响：每个新实例冷启动增加 9 次 schema 检查；通常与当前请求处于同一活跃窗口，主要增加请求负载。

### P1：状态变更与 Bark 更新

- 证据级别：代码与云端均确认存在，但频率低。
- 状态变化额外读取房间和 Bark 集合；每台成功 Bark 设备额外写一次。
- 当前 Bark 订阅仅约 1 条，暂不是主要费用来源。

### P2：索引或慢 SQL

- 当前无证据支持其为主因。
- 缓存命中高、无临时文件、无死锁、无长查询快照。
- 缺少 SQL 级统计，不能完全排除局部慢查询，但不应先于轮询和在线时间写入优化。

## 8. 建议的优化顺序

以下仅为第二阶段建议，本阶段未实施。

### 第一步：合并并节流在线时间写入

- 移除同一请求内对同一 `deviceSessions.lastSeenAt` 的重复写入。
- 将成员和设备在线时间更新节流到 5–10 分钟一次。
- 保持设备列表、管理员最近活跃时间和异常识别可用。

预期：

- 直接降低每次 `getState` 的写操作。
- 降低行版本膨胀、autovacuum 和索引维护压力。
- 若仍保持 5 秒读轮询，不应承诺 PostgreSQL 活跃时间段同步下降。

验证：

- 检查 `documents_3` / `documents_5` 的 `n_tup_upd` 增速。
- 检查 autovacuum 次数、dead tuple 和函数延迟。
- 连续观察至少 3–7 天资源点。

### 第二步：降低无用户时的清理频率

- 在确认最长可接受清理延迟后，将每小时清理评估为每日一次或每 6–12 小时一次。
- 先用隔离测试确认不会错过验证截止时间。
- 不直接删除触发器。

预期：

- 无用户时，清理相关活跃时间段从最多 24 个/天降到 1–4 个/天。
- 理论最大节省约 285–335 点/天；实际节省取决于与其他请求是否重叠。

### 第三步：减少前端无意义同步

- 评估 15–60 秒的可配置/自适应轮询。
- 同一浏览器使用 `BroadcastChannel` 选主，避免每个标签页独立轮询。
- 页面隐藏时保持停止轮询；恢复前台只同步一次。
- 先评估低频兜底 + ntfy 事件触发，不直接把 ntfy 当作可靠实时通道。

预期：

- 显著降低 API 和数据库请求数。
- 只有在部分 5 分钟窗口完全无数据库请求时，才会降低 PostgreSQL 活跃时间段。

### 第四步：节流通知成功时间

- 评估 Bark `lastSuccessAt` 是否需要每次成功后立刻写入。
- 可保留测试通知的即时更新时间，对常规状态通知按 5–10 分钟节流。

### 第五步：索引和 SQL 优化

- 只有取得 `pg_stat_statements`、慢查询日志或明确时序证据后再处理。
- 不盲目增加索引。
